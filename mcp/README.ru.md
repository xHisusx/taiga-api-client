# taiga-api-mcp-server

MCP-сервер для [Taiga](https://taiga.io). Подключает вашу учётку Taiga к MCP-клиенту
(Claude Code, Claude Desktop, Cursor, …) и даёт агенту работать от вашего имени и в рамках
ваших прав: посмотреть, что на вас назначено, двигать статусы, создавать истории, задачи,
баги и эпики, назначать исполнителей, ставить оценки, комментировать и планировать спринты.

Построен на [`taiga-api-client`](../README.ru.md) — типизированном клиенте Taiga REST API из
этого репозитория.

- 🇷🇺 Русская версия — вы здесь · [🇬🇧 English version](README.md)

## Чем это лучше прямого REST

В Taiga почти всё адресуется числовыми ID, и эти ID **свои в каждом проекте**: статус
«In progress» — это разные числа в разных проектах. Сервер закрывает этот разрыв, чтобы агент
работал в тех же терминах, что и человек:

- **Имена вместо ID.** `status: "In progress"`, `assigned_to: "alice"`, `sprint: "Спринт 12"`,
  `severity: "Normal"`, `points: { all: 5 }`. Всё это разрешается по каталогам конкретного
  проекта, а на неизвестное имя приходит ответ со списком допустимых — агент исправляется сам,
  а не угадывает.
- **Один запрос, чтобы изучить проект.** `taiga_project_schema` отдаёт все каталоги сразу
  (статусы по каждому типу сущности, участников и их роли, спринты, типы багов, severity,
  priority, шкалу поинтов, теги и ваши права) и кэширует их на пять минут.
- **`#ref` или `id`.** Номер, который виден в интерфейсе (`#34`), уникален только внутри
  проекта, а API ждёт глобальный id. Любой инструмент принимает и то, и другое.
- **Безопасные апдейты.** При изменении передаётся `version` сущности: если коллега правил её
  параллельно, запрос честно падает, а не перетирает чужие правки.
- **Ровно ваши права.** Всё выполняется от имени аутентифицированного пользователя. `403`
  возвращается как «у вашей учётки нет такого права в этом проекте» со ссылкой на список
  прав проекта.

## Установка

```bash
# из npm
npx taiga-api-mcp-server --help

# из этого репозитория
bun install
bun run build          # собирает taiga-api-client в dist/
bun run build:mcp      # собирает mcp/dist/cli.js
```

Три имени, и это намеренно: пакет в npm — **`taiga-api-mcp-server`** (короткое имя занято
сторонним сервером), команда после установки — **`taiga-mcp-server`**, а имя в MCP Registry —
**`io.github.xHisusx/taiga-mcp-server`**.

## Доступы

Нужен URL инстанса и ровно один способ аутентификации:

| Переменная | Значение |
| --- | --- |
| `TAIGA_URL` | **Обязательно.** Корень инстанса, без `/api/v1`. Taiga Cloud: `https://api.taiga.io` |
| `TAIGA_USERNAME` + `TAIGA_PASSWORD` | Логин **или** email и пароль |
| `TAIGA_APP_TOKEN` | Долгоживущий Application-токен (для ботов и интеграций) |
| `TAIGA_AUTH_TOKEN` (+ `TAIGA_REFRESH_TOKEN`) | Уже имеющаяся пара токенов |

С логином и паролем сервер авторизуется при первом вызове инструмента, а не на старте —
клиент, который его запускает, не зависнет, если Taiga недоступна. Полученная пара токенов
кэшируется в `~/.taiga-mcp/tokens.json` (права `0600`), поэтому перезапуск проходит незаметно;
истёкший токен обновляется, а если обновление не удалось — выполняется повторный вход.
`TAIGA_MCP_NO_TOKEN_CACHE=1` держит токены только в памяти.

> Для всего общего и долгоживущего лучше Application-токен: он привязан к сервисной учётке и
> отзывается в Taiga без смены вашего пароля.

### Поведение

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `TAIGA_WEB_URL` | `tree.taiga.io` для Taiga Cloud, иначе `TAIGA_URL` | Для ссылок на веб-интерфейс |
| `TAIGA_PROJECT` | — | Проект по умолчанию: можно не передавать `project` |
| `TAIGA_TZ` | `+03:00` | Смещение от UTC, в котором `taiga_activity` разрешает окна |
| `TAIGA_MCP_READ_ONLY` | `0` | Регистрировать только читающие инструменты |
| `TAIGA_MCP_ALLOW_DELETE` | `0` | Дополнительно включить `taiga_delete_item` |
| `TAIGA_MCP_TOKEN_FILE` | `~/.taiga-mcp/tokens.json` | Путь к кэшу токенов |
| `TAIGA_MCP_TIMEOUT_MS` | `30000` | Таймаут запроса |
| `TAIGA_MCP_CATALOG_TTL_MS` | `300000` | TTL кэша каталогов проекта |
| `TAIGA_MCP_MAX_RESULTS` | `100` | Жёсткий предел элементов на вызов |

Флаги `--url=`, `--web-url=`, `--project=`, `--token-file=`, `--read-only`, `--allow-delete`,
`--no-token-cache`, `--help` и `--version` переопределяют переменные окружения.

## Подключение клиента

### Claude Code

```bash
claude mcp add taiga \
  --env TAIGA_URL=https://api.taiga.io \
  --env TAIGA_USERNAME=you@example.com \
  --env TAIGA_PASSWORD=... \
  -- npx -y taiga-api-mcp-server
```

### Claude Desktop и любой клиент с JSON-конфигом

```json
{
  "mcpServers": {
    "taiga": {
      "command": "npx",
      "args": ["-y", "taiga-api-mcp-server"],
      "env": {
        "TAIGA_URL": "https://api.taiga.io",
        "TAIGA_USERNAME": "you@example.com",
        "TAIGA_PASSWORD": "your-password",
        "TAIGA_PROJECT": "my-project"
      }
    }
  }
}
```

Локальная сборка вместо npm-пакета:

```json
{
  "command": "node",
  "args": ["/path/to/taiga-ts/mcp/dist/cli.js", "--read-only"],
  "env": { "TAIGA_URL": "http://localhost:9000", "TAIGA_APP_TOKEN": "..." }
}
```

Сервер говорит по MCP через stdio, а всю диагностику пишет только в stderr.

## Если не подключается

`Connection closed` почти всегда означает, что клиент запустил сервер без доступов в
окружении: сервер проверяет конфигурацию и выходит, вместо того чтобы отдавать инструменты,
которыми всё равно не сможет воспользоваться. Причина всегда уходит в stderr, а MCP-клиенты
его сохраняют:

- **Claude Code**: `claude mcp list` покажет здоровье, `claude mcp get <name>` — итоговую
  команду и переменные, а stderr лежит в логе сервера
  (`%LOCALAPPDATA%\claude-cli-nodejs\Cache\<проект>\mcp-logs-<name>\` на Windows,
  `~/.cache/claude-cli-nodejs/...` на остальных системах).
- **`setx` на Windows**: переменная появляется только у **новых** процессов. Уже запущенный
  редактор сохраняет старое окружение, и все MCP-серверы, которые он порождает, тоже —
  перезагрузки окна или перезапуска расширения недостаточно, нужно закрывать редактор
  целиком. Проще вписать значения прямо в запись сервера (`claude mcp add -e KEY=value`) и
  не зависеть от окружения вообще.
- **Неразвёрнутый `${VAR}`**: клиент, который подставляет переменные в конфиг, при пустой
  переменной передаёт её имя как обычный текст. Сервер считает такое значение отсутствующим,
  поэтому вы получите «TAIGA_PASSWORD is missing», а не странный `401` от Taiga.
- **Сервера просто нет в списке**: клиент читает набор серверов один раз за сессию, поэтому
  после правки конфига нужна новая сессия, а не перезагрузка окна. А на Windows Claude Code
  хранит project- и local-записи по буквальному пути воркспейса: расширение VS Code отдаёт
  букву диска в нижнем регистре (`e:\...`), а терминал — в верхнем (`E:\...`), так что
  добавленный из терминала сервер может остаться невидимым для редактора. `claude mcp add
  --scope user` не привязан к пути и обходит это расхождение.

## Инструменты

Чтение (регистрируются всегда):

| Инструмент | Что делает |
| --- | --- |
| `taiga_whoami` | Текущая учётка и ограничения сервера (read-only, удаление) |
| `taiga_list_projects` | Ваши проекты: slug, id, включённые модули |
| `taiga_project_schema` | Все каталоги проекта, нужные для записи, и ваши права |
| `taiga_my_work` | Что назначено на вас, по типам, сначала открытое |
| `taiga_list_items` | Списки историй / задач / багов / эпиков с фильтрами |
| `taiga_get_item` | Одна сущность целиком, при желании с задачами или связанными историями |
| `taiga_search` | Полнотекстовый поиск внутри проекта |
| `taiga_list_comments` | Ветка комментариев и, опционально, изменения полей |
| `taiga_activity` | Что происходило в проекте за период, одним вызовом — [ниже](#активность-что-происходило-за-период) |

Запись (если не задан `TAIGA_MCP_READ_ONLY=1`):

| Инструмент | Что делает |
| --- | --- |
| `taiga_create_item` | Создать историю, задачу, баг или эпик |
| `taiga_update_item` | Статус, исполнитель, спринт, тема, описание, теги, срок, блокировка, поинты — и комментарий тем же вызовом |
| `taiga_add_comment` | Комментарий к сущности |
| `taiga_create_sprint` | Создать спринт (milestone) |
| `taiga_link_epic` | Привязать историю к эпику или отвязать |

Только при `TAIGA_MCP_ALLOW_DELETE=1`:

| Инструмент | Что делает |
| --- | --- |
| `taiga_delete_item` | Безвозвратно удалить сущность. Требует `confirm: true` |

Удаление выключено по умолчанию: в Taiga нет отмены, а почти всегда имелось в виду закрытие
сущности, а не её удаление.

## Как это выглядит в работе

> **«Что мне делать?»**
> `taiga_my_work` → три истории и задача, у каждой статус, спринт, срок и ссылка.

> **«Переведи историю про SSO в In progress и скажи команде, что я её взял.»**
> `taiga_project_schema` (один раз, дальше из кэша) → `taiga_update_item { type: "userstory",
> ref: 12, project: "apollo", status: "In progress", assigned_to: "me", comment: "Беру себе." }`
> → `{ "changed": { "status": "New → In progress", "assigned_to": "none → alice",
> "comment": "added" } }`

> **«Разбей эту историю на задачи текущего спринта.»**
> `taiga_create_item` на каждую задачу с `user_story: 1001` и `sprint: "Спринт 12"`.

> **«Что команда делала на прошлой неделе?»**
> `taiga_activity { projects: ["apollo", "orion"], period: "last_week" }` → по записи на каждую
> затронутую карточку: путь по статусам, что закрыли, комментарии и изменения спринтов.

## Активность: что происходило за период

`taiga_activity` отвечает на вопрос «что сделали за прошлую неделю» одним вызовом — и это
единственный способ получить работы за период: у списочных методов Taiga **нет фильтров по
датам**, а `modified_date` не отличает работу от переноса карточки по доске. Восстанавливать
неделю вручную — `order_by=-modified_date`, прощупывание границы окна, затем история по каждой
карточке — стоит тысячи токенов на карточку и даёт разный ответ в зависимости от того, где агент
решил остановиться.

```jsonc
  "period": "last_week"
}
```

У задачи дополнительно приходит `parent` — родительская история, а при `fold_tasks: true`
задача и вовсе вкладывается под эту историю: именно так пишется недельный отчёт. Для самого
отчёта стоит добавить `include_planning: false` — на загруженной неделе больше половины карточек
только планировали, и без них ответ уменьшается примерно вдвое.

**Завершена** ли история, отвечают `tasks_total`, `tasks_done` и `all_tasks_done`: они считают
весь состав задач истории, а не ту его часть, которую затронуло окно; `tasks_scope: "all"`
вдобавок перечисляет незатронутые задачи. **Закрыта** ли она — отвечают статусы:
`status_events` датирует каждый переход, `closure_only` помечает карточку, с которой в окне
только сняли галочку, — потому что `finish_date` и флаг `is_closed` заполняются руками и чаще
всего не заполняются вовсе.

Оба ответа приходят дважды. `status_now`, `tasks_done` и `all_tasks_done` — про сегодняшний
день; `status_at_until`, `tasks_done_at_until` и `all_tasks_done_at_until` — про момент, когда
окно закрылось. Отчёт пишется про окно, поэтому читать ему вторую тройку: задача, переведённая
в Done в следующую среду, — не работа прошлой недели, как бы завершённо она ни выглядела
сейчас.

При `group_by: "event"` вместо `items` возвращается `events`: голая хронология по возрастанию,
по записи на каждое изменение. У каждой есть вид изменения `kind` (`created`, `status`,
`closed`, `finish_date`, `comment`, `sprint`, `assignee`, `attachment`, `description`,
`subject`, `tags`, `other`) **и** поле `field`, которое менялось, — так что ни одна запись не
приходит безымянным «что-то изменилось».

| Параметр | По умолчанию | Значение |
| --- | --- | --- |
| `projects` | `TAIGA_PROJECT` | Один проект или список (slug, имя или id) |
| `period` | `last_week` | `last_week`, `this_week`, `last_7_days`, `last_14_days`. Скользящие начинаются с местной полуночи N дней назад, поэтому в течение суток ответ не плывёт |
| `since` / `until` | — | Явные границы: `"2026-10-19"` или ISO-8601. Несовместимы с `period`, `until` требует `since` |
| `tz` | `TAIGA_TZ` | Фиксированное смещение от UTC, в котором читаются даты (`"+03:00"`, `"Z"`) |
| `types` | все | `userstory`, `task`, `issue`, `epic`, `milestone` |
| `group_by` | `item` | `item` — свод по карточкам, `event` — хронология |
| `include_comments` | `true` | Включать текст комментариев |
| `include_planning` | `true` | `false` выбрасывает карточки, которые только планировали, — самый дешёвый способ сжать ответ до сделанной работы |
| `fold_tasks` | `false` | Вкладывать задачи под родительскую историю. Задача, чьей истории в выдаче нет, остаётся сама по себе |
| `tasks_scope` | `period` | `all` перечисляет весь состав задач истории: у каждой вложенной задачи появляется `in_period`, незатронутые приходят короткой записью. Три счётчика приходят в любом случае |
| `include_by_finish_date` | `false` | `true` добавляет карточки без единого события в окне, у которых в окно попадает `finish_date` |
| `verbosity` | `full` | `compact` выбрасывает все пустые значения, URL и `status_path` и отдаёт JSON без отступов |
| `tags` | — | Только карточки, несущие **все** эти теги |
| `users` | — | Только события этих авторов (`"me"` — текущий пользователь) |
| `max_pages` | `20` | Страховочный предел, считается в страницах по 100 событий, **которые достают до окна**: промотка более свежих событий в него не входит |
| `comment_chars` | `1500` | Предел длины комментария, дальше ставится `truncated` |
| `drop_noise` | `true` | Поля порядка. `false` принимается только с `group_by: "event"` |

### Что сервер решает сам, чтобы это не решал отчёт

- **Окно локальное и полуинтервальное.** `[since, until)` в часовом поясе `tz`, дата без времени
  — начало суток. `last_week` — с понедельника 00:00 по понедельник 00:00, семь полных суток:
  работа в субботу — это тоже работа той недели. В `window` возвращаются и локальные границы, и
  их UTC-эквивалент: трёх часов разницы ровно хватает, чтобы выбросить утро понедельника из его
  собственной недели.
- **Карточка закрыта, если так говорит её статус.** `closed_in_period` выводится по схеме
  самого проекта: карточка дошла до статуса, который этот проект считает закрывающим. Флаг
  `is_closed` отдаётся рядом, как `closed_flag_in_period`, но не вместо: карточка доходит до
  Done, а флаг не двигается, и наоборот — флаг приходит на карточку, оставшуюся в New. Где они
  расходятся, видно оба значения. `status_events` датирует каждый переход, так что работу можно
  датировать, не доверяя дате завершения.
- **Где карточку оставило окно, а не только где она стоит сегодня.** `status_now` отвечает за
  сегодня, а отчёт — за неделю, поэтому `status_at_until` несёт статус, в котором карточка
  стояла на момент закрытия окна: он выводится из первого перехода **после** окна, а рядом
  идёт `status_at_until_is_closed`. С задачами истории то же самое: `tasks_done_at_until` и
  `all_tasks_done_at_until` рядом с `tasks_done` и `all_tasks_done`. Иначе задача, ушедшая в
  Testing в четверг и в Done в следующую среду, читается как завершённая работа недели, в
  которую она завершена не была.
- **Отменённое закрытие — не закрытие.** Четыре дефекта, переведённые в Closed в 15:06 и
  возвращённые обратно в 15:14, приходят с `closed_in_period: true` **и**
  `reopened_in_period: true`: закрытие было, но докладывать четыре закрытых дефекта всё равно
  неверно. Где их оставили эти восемь минут, говорит `status_at_until`.
- **История завершена настолько, насколько завершены её задачи.** `tasks_total`, `tasks_done` и
  `all_tasks_done` считают весь состав задач истории, а не только задачи, затронутые окном.
  Именно этот критерий и применяет недельный отчёт, и именно его таймлайн сам по себе не даёт;
  обходится бесплатно — список задач проекта всё равно читается.
- **Закрыть карточку — не то же, что поработать над ней.** `closure_only` помечает карточку, у
  которой в окне нет ничего, кроме закрытия: ни комментария, ни вложения, ни событий по
  вложенным задачам. Восемь карточек, закрытых в понедельник с 09:56 до 12:34, — это разбор
  доски, а иначе они прочитаются как работа этого понедельника. То же самое в числах — для
  разбора доски, в котором заодно сменили исполнителя или оставили комментарий:
  `tasks_touched_in_period`, сколько задач истории двигалось в окне, и `work_events_count`,
  сколько событий что-то добавили к карточке — комментарий, вложение, описание, переход
  статуса, кроме закрывающего, — в отличие от флага, даты, исполнителя и спринта, которые
  только учёт.
- **Дата завершения — не событие.** Закрытие задним числом по-прежнему считается (в Done
  переводят спустя дни), но заполнять `finish_date` никто в Taiga не обязан, поэтому карточка
  **без единого** события в окне попадает в выдачу только при `include_by_finish_date: true`.
  Чем ручались, говорит `source`: `"timeline"`, `"finish_date"` или `"both"`, а сама дата
  приходит с карточкой в любом случае.
- **Один комментарий, поправленный, — один комментарий.** События «отредактировано» в Taiga
  нет: текст приходит заново целиком. В ответе остаётся одна запись — с последним `at` и
  пометкой `edited: true`, — и правка не идёт вторым событием: по числу событий отчёт оценивает
  вес карточки.
- **Планирование — не работа.** `planning_only` помечает карточку, которую только перенесли по
  спринтам, переназначили, передвинули по доске или у которой правили описание: ни смены
  статуса, ни закрытия, ни комментария, ни вложения. Оставь это потребителю — и решаться оно
  будет каждую неделю по-разному.
- **Шум не доезжает.** Поля порядка (`*_order`) выбрасываются, `description_diff` — всегда одна
  и та же строка-заглушка, а не текст, — сворачивается в `description_changed`, вложения
  сворачиваются в счётчики, а HTML-версии и URL вложений с токенами не отдаются вовсе. Параметр
  `token` затирается и внутри текста комментария: ссылки на вложения люди вставляют туда
  руками, а комментарий уходит в отчёт дословно, и дальше — по почте.
- **Неполные данные говорят об этом.** Листание останавливается по `since`, а не по числу
  страниц. Если раньше кончился `max_pages`, в ответе и у проекта стоит `truncated`: «за неделю
  ничего не делали» и «данные не доехали» — это разные утверждения для руководства. В бюджет
  попадают только страницы, достающие до окна: недельное окно на проекте с 60 событиями в сутки
  лежит за полутора страницами более свежих событий, и если списывать эту промотку на
  `max_pages`, бюджет кончится раньше, чем начнётся окно. Если даже потолок в 100 страниц ушёл
  на промотку, у проекта стоит `window_reached: false`. Страница, упавшая посреди прохода,
  отдаёт то, что успели собрать, с пометкой `truncated`, а не рушит вызов.
- **Недоступный проект не рушит вызов.** `403` отмечается у этого проекта, остальные отвечают;
  неизвестный slug — ошибка со списком доступных проектов.
- **Ответ, который влезает.** Три проекта за неделю в pretty-printed виде в один ответ
  инструмента не влезают, а большая часть этого текста — `false`, `null` и `[]`.
  `verbosity: "compact"` выбрасывает все пустые значения, URL и `status_path` (`status_events`
  говорит то же самое) и убирает отступы. Ответ сжимается в два-три раза — тем меньше, чем
  больше в нём текста комментариев, — и не теряет ничего из того, что отчёт напечатал бы.
  Признаки, которые читаются как ответ, остаются даже когда ответ отрицательный —
  `in_period`, `closed_in_period`, `reopened_in_period`, `all_tasks_done` и счётчики задач, —
  потому что при `tasks_scope: "all"` отсутствующий `in_period` — плохой способ сказать «эта
  задача не двигалась».

## Какие поля есть у какого типа

Taiga даёт разным типам разные поля, и вызов, который их путает, отклоняется с объяснением,
а не превращается в 400 от API:

| | история | задача | баг | эпик |
| --- | --- | --- | --- | --- |
| спринт (`milestone`) | ✅ | ✅ | ✅ | ❌ |
| `due_date` | ✅ | ✅ | ✅ | ❌ |
| поинты (`points`) | ✅ | ❌ | ❌ | ❌ |
| родительская `user_story` | ❌ | ✅ | ❌ | ❌ |
| `issue_type` / `severity` / `priority` | ❌ | ❌ | ✅ | ❌ |
| `color` | ❌ | ❌ | ❌ | ✅ |

Два правила Taiga, которые сервер проверяет сам, вместо того чтобы молча потерять поле:

- **Задача внутри истории живёт в спринте этой истории.** Попытка задать спринт такой задаче
  отклоняется с подсказкой перенести саму историю; задача без родителя кладётся в спринт
  напрямую.
- **Поинты задаются по роли, а `total_points` — их сумма**, поэтому `{"all": 5}` в проекте с
  четырьмя оценивающими ролями даёт `total_points` = 20. Чтобы оценить одну роль — назовите
  именно её.

## Разработка

```bash
bun run test        # 149 тестов против Taiga в памяти, без сети
bun run typecheck
bun run build
```

Тесты поднимают настоящий `McpServer` и дёргают его через in-memory MCP-клиент, подсунув
клиенту фальшивую Taiga в качестве `fetch`. Так проверяются схемы инструментов, разрешение
имён, тела запросов и маппинг ошибок — без живого инстанса.

Сборка **вшивает `taiga-api-client` из `src/` этого репозитория** (через `paths` в
`mcp/tsconfig.json`), поэтому локальная сборка всегда работает на клиенте из рабочей копии,
а не на версии из npm. Внешними остаются только MCP SDK и zod.
